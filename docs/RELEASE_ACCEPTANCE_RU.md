## Новое обязательное условие: ChatGPT Writer bridge

Проверенная действующая авторизация HEALTH использует GitHub OIDC и Supabase Edge secret, а обычные коннекторы не умеют запускать приватный chat_worker. Целевой путь с GitHub Actions Secrets требует отдельного защищённого OAuth-шлюза, изолированного исполнителя Writer/Verifier и подтверждения точного кандидата. Полная техническая спецификация: [WRITER_CHAT_GATEWAY_RU.md](WRITER_CHAT_GATEWAY_RU.md). **Нельзя считать переписывание промпта фактическим подключением Writer.**

Закрепить в приватном окружении Writer корректные `HEALTH_SOURCE_OWNER_EMAIL` и `HEALTH_SOURCE_VERIFIER_EMAIL` **до** переключения кода. Проверить оба ограниченных профиля без медицинских изменений.
2. Перед merge HEALTH согласовать конкретную процедуру принятия нового SHA: SQL runtime, подписанный брокер, GitHub `HEALTH_WRITER_ACCEPTED_SHA`. Нельзя менять лишь одну из этих величин и объявлять Writer активным. Сначала получить разрешённый change/approval и проверить безопасность взаимосвязанных операций.
3. Слить HEALTH #33 только вместе с контролируемым повторным принятием нового SHA, подтвердить CI и readback фактического runtime; не проводить клинические записи без отдельного реального bounded Writer и независимого проверяющего.

Разработать/проверить безопасный ChatGPT Writer gateway по отдельному проекту: owner OAuth, безопасный приватный request journal, ограниченный исполнитель, независимый verifier, клинический consent, синтетические негативные проверки и внешний аудит. Затем установить новый инструмент в ChatGPT Project с явным разрешением владельца. Перенести Project Instructions вручную из `docs/CHATGPT_PROJECT_PROMPT.md`; проверить `capabilities()` и доступность реального Writer. Не передавать в чат GitHub Actions Secrets.
5. Проверить SHEDULLER #35, включая синтаксис Actions/rclone scope. Перед merge согласовать и переутвердить **SHEDULLER main SHA** для медицинского ежедневного backup, иначе проверка SHA остановит существующий полный архив.
6. После слияния SHEDULLER подтвердить новый полный медицинский backup успешным actual run + удалённым readback/restore. Затем включить `HEALTH_GITHUB_SNAPSHOT_ENABLED` и провести actual run отдельного документационного архива; проверить объект в приватном Backup Drive, SHA байтов и восстановление всех четырёх документов. Контрольные SHA/отчёт фиксировать в приватном техжурнале, не в медицинских REC.
7. Проверить, что ни система управления, ни новая инструкция ChatGPT не требуют старых Drive Docs или GitHub HEALTH_DB_old. Старый `public.system_state.governance_documents_snapshot` может содержать исторические ссылки как доказательства миграции: **не переписывать историческую строку задним числом ради вида**. Действующее управление берётся из принятого GitHub main.
8. После независимого восстановления управляющих документов и отдельного решения владельца решить, оставить старые файлы архивом или удалить. Не удалять сохранившиеся уникальные медицинские оригиналы и исходную доказательную линию без отдельного протокола.

## Принцип допуска к записи
При явной команде владельца на медицинское изменение новый проект должен самостоятельно выбрать Writer **без дополнительной команды**, но выполнить запись сможет только после доступности ограниченного оператора, свежего code pin, точной подписанной авторизации и независимых проверок. GitHub Secrets хранятся только в Actions и не предоставляются в чат. Supabase административный SQL не является резервным способом записи.

**Нельзя заявлять завершение перехода**, пока обе согласованные версии, обе цепочки резервирования и клиентская интеграция Writer не подтверждены живыми проверками.
