# HEALTH — периодические коммиты активности и контроль расписания

## Назначение

Для публичного репозитория GitHub может отключать workflows с `schedule` после 60 дней отсутствия активности. Практическая схема сообщества — создавать настоящий Git-коммит по расписанию. Здесь используются **только Git-коммиты**, без альтернативного механизма повторного включения Actions через GitHub API.

**Важное ограничение:** GitHub описывает общую активность репозитория, но не гарантирует явно, что коммиты в отдельную неосновную ветку всегда предотвращают 60-дневное отключение. Этот механизм — экспериментально проверяемая мера, не гарантия непрерывной работы. Планировщик GitHub может задержать либо пропустить запуск.

## Где что находится

- `HEALTH/main` — содержит только согласованный `.github/workflows/health-activity.yml`; GitHub `schedule` работает **только** из default branch (`main`). Код и тесты `scripts/automation/health_activity.*` живут в `HEALTH/scheduler-code`, запускаются исключительно по принятому полному commit SHA. Кодовой pin независим от SHA Writer.
- `HEALTH/scheduler` — отдельная техническая ветка с README и пустыми коммитами (без изменения файлов). Запрещён merge в `main` или `pwa`.
- `HEALTH/pwa` — публикация сайта, её workflow и содержимое не затрагиваются.

Код Writer закреплён за точным SHA `main`. **Этот документ и workflow не разрешают преждевременное слияние PR в main.** Сначала полноценное согласованное принятие нового Writer SHA и обновление всех связанных авторизаций.

## Частота

Workflow `HEALTH scheduled activity (15-day branch heartbeat)` содержит две задачи по UTC:
- `17 5 * * *` — каждый день в 05:17 UTC проверяет дату последнего коммита `scheduler` и, если прошло хотя бы **15 суток**, создаёт пустой коммит **только в scheduler**. Если срок не наступил, не пишет ничего.
- `43 8 * * *` — каждый день в 08:43 UTC проверяет дату. При достижении **18 суток** завершается с ошибкой `HEALTH_SCHEDULER_OVERDUE`.

Разница в 3 дня нужна, чтобы кратковременные задержки расписания не давали ложных предупреждений. При опоздании основной job после восстановления может создать пропущенный коммит, но выдаст failure по прежнему превышению срока — владелец увидит факт сбоя.

`workflow_dispatch` с `mode=check` позволяет безопасно проверить статус без записи. `mode=heartbeat` сделает коммит **только если действительно прошло не менее 15 дней**. Синтетические границы проверяются `node --test scripts/automation/health_activity.test.mjs`.

## Электронные уведомления

Механизм использует **встроенные уведомления GitHub о неуспешных Actions**: никаких SMTP-паролей и внешнего email-API. Владельцу необходимо самостоятельно открыть **GitHub → Settings → Notifications → System → Actions** и включить email о сбоях workflow. Точное название и расположение опции зависят от текущего интерфейса GitHub; дополнительно проверьте назначенный адрес email.

Уведомления по расписанию направляются пользователю, ставшему `actor` запланированного workflow (обычно автору/изменившему cron либо включившему workflow). Проверьте на тестовом FAIL в отдельной безопасной среде, что почта действительно приходит нужному аккаунту. `main` не стоит менять ради тестового FAIL.

**Ключевой предел:** если GitHub перестанет запускать оба расписания, проверка просрочки тоже не выполнится и сама не пришлёт письмо. GitHub может отдельно предупредить о предстоящей деактивации расписания. Для гарантированного обнаружения полного молчания потребуется внешний наблюдатель, **сейчас не внедрён**.

## Разрешения и безопасность

- Общие разрешения workflow: `contents: read`. Только отдельный job heartbeat имеет `contents: write`.
- Push всегда имеет единственный явный ref `HEAD:refs/heads/scheduler`; ни `main`, ни `pwa` не меняются.
- `main` и `pwa` должны оставаться защищёнными GitHub Rulesets. У нового workflow нет секретов Supabase, Google Drive, OIDC и `id-token`.
- В PR исполняются только синтетические тесты, без прав записи. Запуск автоматизации от `pull_request` запрещён условиями.
- Проверять журналы и SHA после принятия workflow. Не удалять ветку `scheduler` как «слившуюся» при будущей очистке.

## Приёмка

1. Появление workflow на default `main` **только после нового принятия Writer SHA**.
2. Зелёные тесты на PR, невозможность записи из PR, сохранность существующих Rulesets.
3. Первый `workflow_dispatch` с `mode=check` проходит успешно; при сроке менее 15 дней `heartbeat` не делает коммит.
4. После 15 суток появляются реальные коммиты лишь в `scheduler`; `main` Writer SHA не меняется в результате этих событий.
5. При просрочке 18 суток проверка FAIL, письмо на адрес владельца действительно доставляется.
6. Для проверки реального предотвращения отключения `schedule` потребуется долгосрочное наблюдение; не ставить доказательный PASS по первым успешным запускам.

## Контекст будущей консолидации SHEDULLER

Владелец планирует полностью перенести задачи приватного `Alexio000/SHEDULLER` в один публичный `Alexio00/HEALTH`. Этот отдельный keepalive **не переносит резервирование, секреты или восстановление**. Для миграции требуется независимый security-review публичных workflows, изоляции токенов, автоматизации Writer, архивов и привязки backup executor SHA, а также сквозная проверка резервирования до отключения старого Scheduler. Не копировать приватные медицинские payload или значения Secrets в публичный репозиторий.
