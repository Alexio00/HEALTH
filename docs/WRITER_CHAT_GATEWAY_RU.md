# Доступ к медицинскому Writer из ChatGPT через защищённый исполнитель

**Статус:** техническая спецификация, не запущенная интеграция. Дата: 13.10.2026.
**Применимость:** новая конфигурация ChatGPT Project и защищённого Writer; не изменяет действующую базу и текущий код авторизации.

## 1. Проверенный текущий путь

- В публичном `HEALTH/.github/workflows/writer-authorization.yml` есть только `workflow_dispatch` с `request_key`, `kind=intent|candidate`, `digest=SHA-256`. Job с `id-token:write` получает подписанный GitHub OIDC JWT.
- `signed_canonical_authorization.py` передаёт JWT и три непрозрачных поля приватной Supabase Edge Function. Функция проверяет подпись, owner `actor_id`, репозиторий, SHA, workflow и затем вызывает фиксированный RPC с собственной server-side `SUPABASE_SERVICE_ROLE_KEY` в настройках Edge, **не в GitHub Secrets**.
- `scripts/writer/chat_worker.py` — отдельная локальная программа с приватными профилями, ограниченными PostgreSQL Writer/Verifier logins, CA-пином и Google OAuth-файлами. Она создаёт реальный intent/candidate, вызывает GitHub workflow от подтверждённой учётной записи владельца, проверяет Sources и публикует только через ограниченный RPC. Публикация требует независимых семантических доказательств.
- Новый ChatGPT Project с обычными коннекторами GitHub/Google Drive/Supabase **не** получает автоматически право запускать локальную программу, не имеет `workflow_dispatch` в установленном GitHub-коннекторе и не может читать значения GitHub Actions Secrets. Административный `execute_sql` не считается безопасной заменой Writer.

## 2. Выбранная целевая архитектура

**Цель:** пользователь прямо говорит в новом чате «добавь / исправь», и разрешённая операция автоматически использует ограниченный Writer **без отдельной команды включения**, с проверкой фактической личности владельца, точного кандидата и независимых источников. Неизвестный статус или отсутствие интеграции = запрет публикации.

**Не делать:** копировать пароль Supabase из GitHub Secrets в контекст модели; писать медицинские строки в GitHub issue/PR, repository_dispatch, workflow inputs/artifacts/logs; выполнять медицинские INSERT/UPDATE административным плагином; ослаблять RLS или подменять `github.actor_id` машинным ботом.

### 2.1 ChatGPT → проверенный приватный шлюз

Создать отдельный подключаемый инструмент `health_writer_gateway` (MCP/ChatGPT App с собственным OAuth). Установку и разрешения подтверждает владелец. Инструмент предоставляет **узкий интерфейс**, а не общий SQL:

- `capabilities()`: фактические API версии, текущий допуск Writer, accepted SHA, наличие оператора и право пользователя; без секретов или медицинского содержимого.
- `submit_intent(owner_text, conversation_ref, request_key)`: создать единственное неизменяемое owner intent из точной команды. Проверить подтверждённый OAuth user, авторизованный owner UID, ограничения размера/типа, уникальность request_key и логическую операцию; ответ — только закрытый operation/request ID.
- `prepare_candidate(request_key, structured_delta)`: подготовить before/after по ограниченному Writer; хранить полный медицинский payload в приватной Supabase/допущенном защищённом хранилище, **не в GitHub**.
- `review_status(request_key)`: прочитать текущий точный кандидат и недостающие независимые подтверждения; допускается вернуть владельцу медицинские сведения в его закрытый чат, но не в технические Actions logs.
- `confirm_candidate(request_key, candidate_sha)`: точное согласие владельца на публикацию неизменённого кандидата через подтверждённый пользовательский поток. Само наличие OAuth-сессии или ответ модели без проверки подтверждения не должно заменять решение владельца.
- `publish_status(request_key)`: показать состояние, `operation_id`, Validation, FINALIZED и повторный readback. Повторный вызов идемпотентен.

Применить частотные лимиты, журнал отказов, привязку пользователя и области операции, nonce/expiry/replay protection; запрещать выбор схемы, SQL, произвольных URL и административных ролей из данных запроса. Нельзя считать свободный текст доказательством подписи владельца без проверенного канала подтверждения.

### 2.2 Приватный исполнитель с GitHub Actions Secrets

**Если выбран путь GitHub Secrets:** исполнять ограниченный Writer в приватном `Alexio000/SHEDULLER` либо в другом изолированном приватном рабочем контуре, а не в публичном HEALTH. Использовать выделенный `environment` и только минимальные секреты (конкретные имена выбираются при настройке):

- ограничённый Writer PostgreSQL login + проверенный TLS CA;
- отдельный ограничённый Verifier PostgreSQL login + независимый Google reader;
- отдельно Google Drive Source uploader для Writer без права заверения; verifier не должен видеть writer secret;
- никакого `postgres`, `service_role` или резервного полного backup credential в работе клинического Writer.

Два разных задания/изолированных профиля для писателя и проверяющего, с независимыми логинами и журналами. Приватный оператор считывает пакет из **приватного шлюза/очереди** по одноразовому ограниченному идентификатору, не из входных параметров GitHub. Workflow может передать только opaque key и digest. Выполнять строго принятую версию HEALTH, запрещать PR/fork-исполнение с секретами, выключать расширенный журнал, запрещать медицинские artifacts/cache. После работы сверять результат через Supabase, удалять эфемерные файлы. Захват полного backup и Writer согласован общей блокировкой.

**Важно:** периодический запуск GitHub или машинная диспетчеризация от бота не создаёт GitHub OIDC claim `actor_id=308028794`. Нельзя ложно выдавать их за существующую подпись владельца. Текущий signed-owner workflow либо вызывается отдельно настоящим владельцем по подтверждённой GitHub OAuth-сессии, либо новая схема согласия/подписи владельца проектируется, проверяется независимым аудитором и вводится с новым контрактом/миграцией. До этого автоматическая публикация невозможна.

### 2.3 Доступ к сервисам

Новый ChatGPT-проект может иметь общие коннекторы Supabase/GitHub/Drive для чтения и обслуживания, но **клиническую запись** делает только `health_writer_gateway`, а не прямой SQL/редактирование Docs. Обычные коннекторы не вытягивают секреты из GitHub. Профили, роли и JWT не отдаются модели. Source-read и Source-create через контролируемую интеграцию с Drive, а не через публичные файловые ссылки.

**Итог:** GitHub Secrets доступны исполнителю в runtime; чату доступен только узкий авторизованный инструмент и безопасные идентификаторы. Это выполняет пожелание об использовании секретов GitHub, не нарушая медицинскую приватность.

## 3. План внедрения (без даунтайма)

1. Зафиксировать новую модель угроз и точную схему owner consent; предоставить независимому аудитору. Сверить текущую GitHub OIDC подпись и предельные права каждой роли. Решить отдельно, требуется ли сохранение владельческого `workflow_dispatch` или новый криптографический канал подтверждения.
2. В отдельной ветке реализовать OAuth/MCP шлюз, частный request journal/очередь и строго ограниченные действия. Использовать существующие Writer RPC без прямого SQL DML. Не деплоить в production до тестов.
3. Приватный Actions-исполнитель и минимальные отдельные секреты Writer/Verifier; создать в SHEDULLER отдельный workflow, не затрагивая `complete-backup` и его секреты. Запуск только по надёжно проверенному trigger, не через публичный PR.
4. Синтетические сквозные тесты в изолированной Supabase TEST/фикстуре: валидный owner intent, проверка кандидата, неверный владелец, изменение хеша, replay, истечение, отсутствующий секрет, пропавший verifier, Source byte mismatch, SQL DML denial, конкурирующий writer, restart/UNKNOWN, восстановление после потери связи, запрет PHI в GitHub.
5. Отдельный независимый аудит безопасности, затем контролируемая установка в production, принятие нового SHA и runtime, проверка реальных ролей без медицинского изменения.
6. Вручную установить новое подключение `health_writer_gateway` в ChatGPT-проекте и подтвердить OAuth владельца. Тест `capabilities()` должен вернуть доступность; без него проект обязан сообщить read-only.
7. Одно явное owner-approved медицинское тестовое поручение с действительными клиническими данными — только отдельной командой владельца после готовности, с полной независимой проверкой и финальным readback. Не использовать синтетический PASS вместо него.
8. После успешного запуска нового доступа завершить PR #33/#35, перевести управляющие указатели, перепроверить оба backup и убедиться в отсутствии живых зависимостей от старых `HEALTH DB` Docs/Registry. Удалять исторические файлы и оригиналы только по отдельному решению.

## 4. Приёмочные критерии

`PASS` требует одновременно:
- ChatGPT-чат **сам** видит отдельное действие `health_writer_gateway` (а не только обычные три плагина), без доступа к паролю базы;
- owner OAuth/token и точное подтверждение связаны с неизменным owner intent/candidate, нет способа вызвать запись от другого пользователя;
- Writer и Verifier имеют различные минимальные права, реальные независимые доказательства, блокировку конкуренции и fail-closed;
- секреты и медицинский payload отсутствуют в публичном GitHub, workflow input, логах, артефактах и ошибках;
- end-to-end публикация из допустимого инструмента, актуальный `operation_id`, `FINALIZED`, Validation и readback действительно проверены;
- основной ежедневный медицинский backup и независимое резервирование **GitHub-документации** сохранены/перепроверены, recovery намеренно блокирует Writer.

**До PASS:** считать интерфейс ChatGPT read-only для медицинских мутаций, даже если Supabase отмечена `ACTIVE` и существующий локальный Writer включён. Не переписывать старые PASS и не активировать новую схему через простую редакцию Project Prompt.
