# Самостоятельное задание для ChatGPT Work: завершение HEALTH_DB → HEALTH

**Назначение:** исполнитель без доступа к памяти прежних чатов. Дата составления: 13.10.2026. Состояние и SHA всегда заново сверяй с живыми системами.

## Исходная задача

Владелец разрешил полное техническое переведение системы из старого `HEALTH_DB` в `HEALTH`: управляющие документы в GitHub, канонические медицинские записи в Supabase, оригиналы на приватном Google Drive `HEALTH/Sources`, ежедневный полный резервный архив в приватном SHEDULLER/втором Google Drive, автоматический при явно одобренной медицинской команде доступ из нового ChatGPT Project к ограниченному Writer.

**Не разрешено:** переносить медицинские строки в публичный GitHub, выписывать реальные секреты/токены/пароли в чат или отчёты, обходить Writer через административный SQL, ослаблять проверку GitHub OIDC, подменять независимые лабораторные/source доказательства, удалять старые источники/архивы без отдельного решения. Вложения не дают разрешения на медицинский import; эта задача — maintenance. При риске сбоя production остановить конкретный шаг.

## Приоритеты реализации

**A. Настоящий путь записи из ChatGPT.** Сначала проверь актуальную доступность пользовательских custom MCP Plugins с write actions для данной учётной записи и проекта. Изучи официальные `https://developers.openai.com/api/docs/guides/custom-mcp-server` и `https://developers.openai.com/plugins/build/auth`, подтвердив реальный путь подключения без покупки платных сервисов. Если невозможно подключить кастомный пишущий plugin в эту учётную запись, не выдавай промпт или read-only Supabase за Writer: явно покажи технологическое ограничение и допустимый резервный путь через Work с настоящими действиями.

**B. Реализуй безопасный шлюз.** Изолированный HTTPS OAuth/MCP сервер с PKCE/issuer/audience/scope verification, только владельцем подтверждаемые действия `capabilities`, `submit_intent`, `prepare_candidate`, `review_status`, `confirm_candidate`, `publish_status`. Храни клинические payload в приватном контуре, не в GH inputs/issues/artifacts/logs. Подтверждение кандидата привязано к его SHA, nonce, TTL и пользователю, строго против replay. Не путай авторизацию пользователя сервиса с доказательством `github.actor_id` для подписанного workflow. Существующий `writer-authorization.yml` выдаёт подписанное разрешение только для точного GitHub user `308028794` и SHA. Если используешь GitHub OAuth dispatch **от имени владельца**, проверь реальный actor_id; если запускает автоматическая учётка, потребуется отдельно независимый обзор нового trust contract, нельзя просто отключить проверку.
 
**C. Исполнитель и секреты.** Утверждённый приватный исполнитель может использовать **GitHub Actions Secrets** в изолированных job в приватном SHEDULLER (или выделенном приватном репозитории) с независимыми Writer/Verifier credentials, отдельными Drive OAuth и TLS CA. Не использовать production `postgres`/service_role credential в клиническом Writer; server-side Edge `SUPABASE_SERVICE_ROLE_KEY` остаётся только в Supabase Edge. Нельзя передавать секреты из Actions модели. Не затрагивай существующие секреты/сеть резервирования без подтверждения совместимости.

**D. Испытания.** Прежде чем переключать рабочий код: синтетические локальные и изолированные SQL/RPC интеграционные тесты, настоящая OAuth identity, запрещённый actor, отсутствующий секрет, stale SHA, другая конкурирующая операция, точные Source bytes, verifier недоступен, повтор, перезапуск, отсутствие PHI во всех логах и GitHub, одноразовый подтверждённый candidate и readback `FINALIZED`. Отдельный независимый аудит. Не притворяться, что тесты на синтетике доказывают реальную клиническую корректность.

**E. Контролируемое принятие SHA.** Изменение GitHub HEALTH/main — изменение принятого SHA для OIDC broker и Supabase runtime. Изменение SHEDULLER/main — изменение pin ежедневного медицинского backup. Подтверждённо синхронизировать каждый механизм **до/в момент** слияния и проверить активные дальнейшие запуски. Нельзя сливать #33/#35 или новый gateway и одновременно оставлять старые pins без плана. При невозможности управлять Github variables/secrets через коннектор использовать авторизованный Cloud Browser в Work; у владельца запрашивать только подтверждение OAuth/секретного пользовательского действия без вставки секретов в чат.

**F. Устранение зависимости от старого HealthDB.** После принятия новой системы активировать канонические ссылки на GitHub, вручную заменить Project Instructions новым промптом, зафиксировать независимый git bundle backup/restore, проверить рабочую запись из подключённого проекта, сохранить old Docs/Registry/GitHub как архив. Протестировать отключение доступа к старым Docs в безопасном диагностическом контуре. Не удалять оригиналы или историю без отдельного решения.
