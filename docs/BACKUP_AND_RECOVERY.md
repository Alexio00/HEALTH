# Полное резервирование и восстановление HEALTH

## Действующий медицинский архив
Приватный SHEDULLER ежедневно создаёт один согласованный архив: PostgreSQL (схемы и таблицы), Auth, переносимые роли/членства и параметры, история миграций, полный действующий корпус Sources, связи Source ID/локаторов, замороженная историческая линия и контрольные суммы. Используется ограниченная read-only роль с общей блокировкой записи Writer.

Каждый запуск загружает архив-кандидат на независимый приватный Drive, **скачивает его полностью обратно**, проверяет структуру, байты и связи Source, восстанавливает SQL и роли в изолированной среде и проверяет жизненный цикл Auth по HTTP. Только после успешного испытания новый набор становится ACTIVE, а прежний отправляется в Drive Trash. Ошибка сохраняет прежний рабочий архив; безвозвратного удаления и очистки корзины нет. Ёмкость резервного Drive принята владельцем без автоматического запроса квоты.

Расписание: **03:00 Europe/Moscow (00:00 UTC)**; GitHub может запустить с задержкой. Действительный SHA приватного SHEDULLER должен совпадать с принятой переменной контроля; перемена `main` без нового принятия заблокирует полное ежедневное задание.

Текущая ежедневная проверка восстанавливает байты и SQL-граф из архива, но не создаёт полную облачную копию всех Source ежедневно. Создание и независимое чтение нового облачного Source root проверяется при принятии восстановления/нового механизма.

## Восстановление
Сначала точно сверить содержимое архивной базы, ролей и отпечатки. После восстановления **выключить Writer, сбросить принятый SHA и разрешения загрузки**. Незавершённые операции, NNN, разрешения, журналы и resumable sessions должны сохраниться. Перед отдельным повторным включением нужно проверить воссозданный Source root, принятый код и согласовать все pending операции. Восстановление никогда не продолжает медицинскую запись автоматически.

Реализация: приватный [SHEDULLER — полный архив](https://github.com/Alexio000/SHEDULLER/blob/main/docs/COMPLETE_BACKUP_PIPELINE.md); [Auth](AUTH_RECOVERY.md); [Writer](WRITER_OPERATOR.md). Старые архивы не являются доказательством нового запуска — сверяйте точный run, принятое дерево кода, манифест, полный readback и фактическое восстановление.

## Особый контур: документация GitHub
**Медицинский архив SHEDULLER не является полным резервированием репозитория HEALTH.** Управляющие файлы GitHub и историю коммитов необходимо отдельно выгружать в независимый закрытый архив и проверять восстановлением/хешированием. Пока этот контур не реализован и не принят, его статус — **НЕ ПОДТВЕРЖДЕНО**; нельзя удалять старые экземпляры управляющих Google Docs только из-за наличия GitHub main.

Исторические Records/Registry/оригиналы сохраняются до отдельного решения владельца; резервная ротация не разрешает их удалять.

## Кандидат переноса Scheduler (ещё не включён)

Разработка в HEALTH разделена: исполняемый код `scheduler-code` и trusted launchers `main`; ветка `scheduler` содержит только heartbeat. [Issue #65](https://github.com/Alexio00/HEALTH/issues/65) фиксирует условия постепенного переноса. [Issue #87](https://github.com/Alexio00/HEALTH/issues/87) требует независимо проверенного accepted-main SHA и legacy-pause gate для запланированных заданий. **Draft #72/#73/#89 и соответствующие поправки не означают, что новый backup включён.** До успешного полного независимого восстановления, single-active проверки, подтверждения отсутствия выполняющихся задач старой системы и отдельного разрешения владельца SHEDULLER остаётся действующим. Пропущенный (`skipped`) workflow — не доказательство успешного резервирования и сам по себе может не сформировать письмо о сбое.

## Границы доказательств ежедневного восстановления

Полный архив включает структуру/данные SQL, Auth, роли/членства и параметры, историю миграций, корпус оригинальных Sources, их граф идентичностей и контрольные суммы. Проверяется выгрузка полного архива обратно из независимого Drive, проверка каждого участника/Source-байта, изолированное восстановление ролей/базы и Auth HTTP lifecycle. Отсутствие отдельной полноценной пересборки облачного Source root **каждый день** не означает её успешного выполнения; такой сценарий проверяется при принятии нового recovery-механизма. Доказательства каждого запуска должны подтверждать принятый executor pin, полную проверку ACTIVE, rotate-to-Trash; синтетический PASS этого не заменяет.

Восстановление сохраняет незавершённые операции, NNN ledger, authorization/review audit и resumable journal. Оно **отключает Writer**, сбрасывает code pin и Source upload authority до отдельного повторного принятия. Историческая [B-04/A-05 документация](https://github.com/Alexio000/SHEDULLER/blob/main/docs/AUDIT_B04_A05_RECOVERY.md) относится к прежней миграционной проверке, а не текущему расписанию.
