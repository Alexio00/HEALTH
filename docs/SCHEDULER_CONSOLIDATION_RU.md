# Объединение SHEDULLER и HEALTH — эксплуатационный план

**Статус:** подготовлен код-кандидат. Никакие новые задания не активированы и действующий приватный SHEDULLER не отключён. Это документ переноса двух регулярных функций, а не разрешение на production-переключение.

## 1. Состав регулярных функций

| Функция | Старый источник | Кандидат в HEALTH | UTC | МСК |
|---|---|---|---|---|
| Read-only keepalive Supabase | приватный `SHEDULLER/.github/workflows/keepalive.yml` | `.github/workflows/health-supabase-keepalive.yml` | 00:37 ежедневно | 03:37 |
| Полная резервная копия и проверка восстановления | приватный `SHEDULLER/.github/workflows/daily-backup.yml` | `.github/workflows/health-complete-backup.yml` | 00:00 ежедневно | 03:00 |

Дополнительные workflows SHEDULLER (архивные инструменты full migration, ручной тест восстановления, технические пробы) не являются третьим регулярным заданием. Их нужно классифицировать и сохранять как evidence/инструменты до отдельного решения о полном отказе от приватного репозитория.

Код перенесён из зафиксированного `Alexio000/SHEDULLER/main` SHA `8656a360c2b24c0f51e6e2b80edf78e6bd89ccc4` в `scripts/scheduler/`, с изъятием приватных констант и отдельными синтетическими тестами. Исторические оригиналы на английском оставлены без изменений в старом репозитории.

## 2. Конфиденциальность и подготовка публичного репозитория

Нельзя копировать из приватного SHEDULLER исходные значения секретов, адреса медицинских оригиналов, приватные ID папок Drive, хеши закрытых оригиналов, токены rclone или ZIP архивы в публичный репозиторий HEALTH, даже в Draft PR. В подготовленной версии идентификаторы приватных Drive объектов, адреса владельцев и lineage pin извлекаются **из закрытых настроек Actions**. Для нового пациента нужны новые значения, для действующего владельца — только утверждённые текущие.

Публичная ветка `main` остаётся основной, workflow с `schedule` должны находиться именно там. Задачи используют GitHub-hosted runner, read-only `GITHUB_TOKEN`, без OIDC или клинического service-role в browser. Ни один production job не исполняется из PR. Внутренние секреты GitHub необходимо выделить в два ограниченных Environments (с ограничением веток):
- `health-private-automation` — read-only keepalive;
- `health-private-backup` — полный архив с доступом к приватному backup Drive.

Выбор free-плана не означает готовой настройки Environments. **Подтвердить у владельца** фактические веточные ограничения, перечень разрешений, передачу закрытых значений, отсутствие доступа к секретам у непроверенных PR, а также защиту workflow от подмены (связанное HIGH ограничение [#50](https://github.com/Alexio00/HEALTH/issues/50)).

## 3. Требуемые имена параметров без значений

**Keepalive** — в `health-private-automation`:
- Secrets: `HEALTH_KEEPALIVE_DB_URL` (ограниченный `health_backup_reader` Session pooler), `HEALTH_SUPABASE_CA_PEM` (точно проверяемый CA);
- Repository Variable: `HEALTH_KEEPALIVE_ACCEPTED_SHA` (точный SHA принятого **неизменяемого коммита с кодом keepalive**, доступного как предок защищённой `main`, не обязательно текущий Writer SHA);
- Repository variable: `HEALTH_INREPO_KEEPALIVE_ENABLED` — строго `true` лишь после завершённой приёмки.

**Backup** — в `health-private-backup`:
- Secrets: `HEALTH_BACKUP_DB_URL` (ограниченный `health_backup_reader`), `HEALTH_SUPABASE_CA_PEM`, `HEALTH_BACKUP_RCLONE_CONFIG`, `HEALTH_PRIMARY_SOURCE_FOLDER_ID`, `HEALTH_FROZEN_LINEAGE_SHA256`, `HEALTH_FROZEN_ORIGINAL_COUNT`, `HEALTH_BACKUP_PARENT_FOLDER_ID`, `HEALTH_PRIMARY_DRIVE_OWNER_EMAIL`, `HEALTH_BACKUP_DRIVE_OWNER_EMAIL`.
- При наличии уже принятого ACTIVE полного архива seed автоматически читается из ACTIVE; для начального переноса без ACTIVE нужны отдельные исторические seed-параметры и независимое принятие, **не создавать фиктивный seed**.
- Repository Variable: `HEALTH_BACKUP_EXECUTOR_SHA` (точный SHA принятого **неизменяемого коммита с backup executor**, доступного как предок защищённой `main`, независимо от следующих версий Writer);
- Repository variable: `HEALTH_INREPO_BACKUP_ENABLED` — строго `true` лишь после независимого восстановления и перевода единственного писателя ротации.

**Не публиковать значения параметров** даже в тикетах, PR, документации и скриншотах. Все секреты создавать вручную через защищённый интерфейс владельца; ChatGPT здесь не читает и не переносит их.

## 4. Причины запрета преждевременного включения

1. **Writer main SHA.** Любой merge этой ветки в `main` меняет точный принятый Writer SHA. Нужен отдельный согласованный выпуск Writer с новым signed approval, policy, runtime подтверждением. Не сливать проект автоматически.
2. **Полная резервная копия привязана к исполнительному коду.** SHA и внутренний `executor_binding()` изменились из-за переноса файлов, поэтому текущая запись активации на Backup Drive для SHEDULLER не доказывает принятие нового HEALTH executor. Режим `daily` намеренно **откажет** до новой полной `activate` проверки изолированного восстановления. Это требование безопасности, а не ошибка.
3. **Два владельца ротации недопустимы.** GitHub `concurrency` из разных репозиториев не работает как общий замок. Одновременное включение двух независимых ежедневных задач рискует создать гонку. Исходный backup должен оставаться действующим до отдельного окна согласованного переключения; новая интеграция не имеет права конкурировать с ним за один ACTIVE архив.
4. **Публичный код и секреты.** Дополнительные PR, изменяющие любую ветку с доступом к production Environments, требуют независимой оценки и ограничений; нельзя считать green CI защитой от злоупотреблений.
5. **Ограничения GitHub Free и 60 дней.** Для публичного HEALTH scheduled workflows могут отключаться при 60 днях неактивности. Отдельный PR #64 готовит 15-дневные коммиты только в ветку `scheduler`, но это пока не доказанная гарантия; контроль полной потери расписаний внутри того же репозитория не независим.

## 5. Безопасная последовательность перехода

1. Зелёный синтетический CI для `scripts/scheduler/` и `scripts/automation/`, аудит публичных строк на раскрытие private Drive/Source credentials и проверка полномочий новых workflow.
2. Независимо подтвердить точный набор старых workflows, последнюю успешную сохранённую полную копию и доказательства фактического восстановления.
3. При новом Writer acceptance включить этот код в `main`, сохранив оба флага новых задач `false`; убедиться, что старый SHEDULLER продолжает свои scheduled backup и keepalive.
4. Создать два закрытых Environment, веточные ограничения main, секреты и SHA-переменные. Проверить `workflow_dispatch` в изолированном TEST/синтетическом режиме, без production API и Source.
5. В отдельно одобренное безопасное окно выполнить новый `candidate → независимое восстановление → activate` с проверкой всех DB/Auth/ролей/Sources/Writer locks и exact archive provenance. Эти шаги **не запускаются** автоматически этим PR; потребуют отдельного протокола и утверждения владельца.
6. После принятия новой защищённой ротации перевести `HEALTH_INREPO_BACKUP_ENABLED` в `true`, остановив конкурирующую старую ротацию в скоординированном окне. Нельзя допускать ни дня без актуального архивного комплекта и ни одного неуправляемого двухстороннего trash.
7. Аналогично активировать keepalive после проверки restricted read-only login, затем выключить старую задачу Supabase keepalive.
8. Убедиться в двух последовательных успешных суточных запусках, archive readback, independent restoration, отсутствии клинических записей/секретов в публичных logs/artifacts. Зафиксировать ссылки на Actions runs и финальные SHA.
9. Старый SHEDULLER разрешается архивировать или удалить **только после отдельного решения владельца**. Сохранять историю, оригинальные evidence и резервный откат.

## 6. Что проверено и что ещё не доказано

- Подготовлена версия с закрытыми конфигурационными значениями; старые исходные документы/свидетельства остаются неизменными.
- Новые работы пока **не имеют runtime-доказательства**: нет изолированного полного восстановления перенесённого исполнителя, свежей проверки production Environments, реальной ротации и независимого аудита новой границы публичного GitHub.

## 7. Доработка кандидата при технической проверке 13.10.2026

**Подготовлены ещё два изолированных пути:**

- `.github/workflows/health-backup-preflight.yml` — ручной **read-only preflight**, без загрузки архива и без Drive rotation. Сначала проверяет точный принятый SHA, владельца запуска и отдельный флаг `HEALTH_INREPO_PREFLIGHT_ENABLED=true`; при ошибке не печатает приватные traceback. Внутри одноразового runner создаётся временный архив для проверки Source ↔ DB связей. Полные данные **не** загружаются в GitHub artifacts.
- `.github/workflows/health-backup-activate.yml` — **только ручная однократная активация**, с обязательной явной строкой подтверждения, проверкой владельца, точного SHA, отдельным флагом `HEALTH_INREPO_ACTIVATION_ENABLED=true`, защищённым `health-private-recovery`. Её нельзя запускать при работающем старом backup. Она делает фактическую независимую проверку восстановления и может заменить ACTIVE архив с перемещением прежнего в корзину. **Не запускать без отдельного согласия владельца непосредственно на эту операцию.**

**Дополнительное окружение для разовой активации** `health-private-recovery` не входит в два постоянных ежедневных окружения. Оно требуется лишь при отдельной процедуре cutover и должно быть создано/проверено владельцем после security-review. Секреты совпадают с `health-private-backup`, плюс `HEALTH_COMPLETE_RECOVERY_RCLONE` — ограниченная конфигурация ролевого доступа, необходимая для *действительного восстановления Sources в отдельную тестовую папку*, не для ежедневного backup.

Новые repository variables `HEALTH_INREPO_PREFLIGHT_ENABLED` и `HEALTH_INREPO_ACTIVATION_ENABLED` отсутствуют по умолчанию и должны оставаться `false` до нового поэтапного разрешения. **Ни один из новых jobs не должен считать наличие секретов разрешением на запуск.**

**Особые поправки в коде:**
1. Для каждого запуска используется фактический `github.sha`, а не динамическая ссылка на движущуюся `main`; это предотвращает гонку между выбором исполнителя и checkout.
2. Проверка `GITHUB_ACTOR_ID` для автоматического cron отличается от ручного запуска: владелец обязателен при `workflow_dispatch`, но сам cron может назначить иного actor; при этом SHA/ref/защищённый код обязательны в обоих случаях.
3. Кандидат, созданный исходным SHEDULLER либо любым отличным SHA, **не принимается** в `HEALTH`: проверяются `health_pipeline_commit`, SHA-256 архива и статус, с отдельными синтетическими негативными тестами.
4. Счёт исторических оригиналов нельзя оставлять зашитым в коде — это закрытый контрольный вход `HEALTH_FROZEN_ORIGINAL_COUNT`; дополнительный тест подтверждает корректный отказ при несоответствии.
5. В публичные логи можно выводить только общие статусы. Полные архивы, метаданные, локаторы и подробные доказательства хранятся только в защищённом временном контуре и/или разрешённом приватном Backup Drive.
6. После любого изменения `HEALTH/main`, включая документацию, `HEALTH_BACKUP_EXECUTOR_SHA` и Writer acceptance могут устареть. Планировщик должен отказывать в выполнении до повторного согласованного принятия. Для непрерывного backup нужна отдельная политика выпуска, согласованная с владельцем.

**Оставшиеся стоп-факторы:** отсутствие admin-readback созданных окружений/Variables, неизвестное фактическое наличие Secrets, отсутствие свежей независимой full restore при новой реализации, не закрытый HIGH scope-check [#50](https://github.com/Alexio00/HEALTH/issues/50), отсутствие owner-approved exact Writer SHA и подтверждённого безопасного окна для отключения старого SHEDULLER. Зелёная синтетика их не отменяет.

## 8. Долговременная независимость резервирования от Writer main SHA

Исправленная реализация **не выключает резервирование при обычных последующих merge в `main`**:
- В workflow `on.schedule` и `on.workflow_dispatch` сохраняется требование `github.ref == refs/heads/main`, но `actions/checkout` теперь получает `ref: ${{ vars.HEALTH_BACKUP_EXECUTOR_SHA }}` — **неизменяемый полный SHA** отдельно принятого кода.
- После checkout проверяется `git rev-parse HEAD == HEALTH_BACKUP_EXECUTOR_SHA`; `complete_pipeline.py` берёт producer SHA из `HEALTH_BACKUP_PRODUCER_SHA`, равного тому же одобренному SHA, а не из меняющегося `GITHUB_SHA` текущего события.
- Supabase keepalive аналогично получает `ref: ${{ vars.HEALTH_KEEPALIVE_ACCEPTED_SHA }}`, а сам скрипт сверяет фактический checkout и роль.
- Синтетическая проверка подтверждает, что изменение event `GITHUB_SHA` после очередного Writer merge **не отменяет принятого** резервного исполнителя, пока код backup/keepalive и политика доступа не менялись.

Владелец должен впоследствии установить обе переменные SHA **на уровне Repository → Actions Variables** после объединения и независимого принятия всего набора PR. Оптимально выбрать полный SHA принятого merge-коммита, остающегося предком `main`, чтобы GitHub никогда не потерял этот объект. Не брать SHA временной ветки, которая может быть удалена после squash-merge. Значения SHA не являются секретами, но сами переменные меняются только в рамках согласованного выпуска.

Секреты в `health-private-automation` и `health-private-backup`, а при одноразовой активации в `health-private-recovery`, остаются в соответствующих защищённых Environments. `HEALTH_INREPO_*_ENABLED=false` до принятия и наличия runtime evidence.

**Остаточный риск:** GitHub Actions workflow файл всё равно запускается из меняющейся `main`, поэтому каждое изменение workflow/Ruleset нуждается в независимом контроле. Доверенный pin кода не заменяет закрытие HIGH [Issue #50](https://github.com/Alexio00/HEALTH/issues/50) и ограничение прав на Secrets.
