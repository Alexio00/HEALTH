# Архитектура HEALTH

## Компоненты и границы
1. **Публичный GitHub HEALTH:** код, техническая документация и публичные справочные снимки (не заменяют приватные Project State/Manual), канонические SQL-миграции, проверки и синтетические тесты; не медицинские данные.
2. **Приватная Supabase HEALTH:** единственная действующая база, полный `records.body_text`, производные таблицы, ID-реестр, операции и независимые доказательства Writer. Source ID не равен физическому объекту Drive.
3. **Приватный Drive HEALTH/Sources:** оригинальные файлы, отдельные идентификаторы и PRIMARY-локаторы, проверяемые SHA-256 и размером.
4. **PWA на GitHub Pages:** авторизация владельца через Supabase Auth, только SELECT, собственный JavaScript, никаких скрытых административных ключей или медицинских данных в статических файлах.
5. **Ограниченный Writer:** явное поручение владельца запускает стандартный путь записи автоматически, если доступен приватный оператор. Операции выполняются через ограниченные SQL RPC с точным intent/candidate, подписанной GitHub-авторизацией и отдельными Reviewer/Source-verifier. Публикация с текущими доказательствами атомарна. Никаких прямых SQL-медицинских прав у chat-оператора нет.
6. **Приватный SHEDULLER:** резервирование и независимая проверка восстановления полной базы, ролей/Auth и Sources на втором Drive.
7. **Supabase Auth:** один владелец интерфейса; `app_readers` ограничивает разрешённого пользователя, идентичности Auth и медицинских записей разделены.

## Модель доверия
- Browser: только публичный клиентский ключ и сессия владельца.
- Публичный GitHub: никакой персональной клиники, персональных аккаунтов, локаторов и секретов. Для Writer — только непрозрачный request key, kind и SHA-256.
- GitHub Actions Secrets: значения доступны только разрешённым заданиям; сам подключённый к ChatGPT GitHub-плагин не может выдавать их содержимое. Никогда не выводить в лог или модель.
- Приватный Writer: отдельные ограниченные подключения Writer/Verifier, доверенные локальные настройки и журнал. Доступ к коду GitHub/Supabase/Drive сам по себе **не подключает** этот оператор.
- Supabase: RLS и deny-by-default; прямой административный SQL не является разрешённой операцией медицинской записи.

## Переносимость и восстановление
`supabase/migrations/` — полная каноническая история миграций схемы; `db/migrations/` — исторические агрегированные снимки. Полная резервная копия содержит базу/Auth/роли/Sources, но не гарантирует резервирование самого GitHub-кода. Восстановление специально выключает Writer, снимает code pin и upload folders, затем требует нового принятия. Исторический `HEALTH DB` не является зависимостью текущей системы; не удалять доказательства без отдельного акта.

## Направление развития: раздельные релизы (проект)

Постоянные ветки: `main` (принятый Writer и trusted launchers), `writer-code` (изолированная разработка Writer), `pwa` (интерфейс), `scheduler-code` (исполняемый код Scheduler), `scheduler` (служебный heartbeat). В `writer-code` и `scheduler-code` ещё нет принятых production-релизов. Перенос Scheduler из приватного SHEDULLER в HEALTH рассматривается в [Issue #65](https://github.com/Alexio00/HEALTH/issues/65), [Draft #72](https://github.com/Alexio00/HEALTH/pull/72), [#73](https://github.com/Alexio00/HEALTH/pull/73); он пока не активирован. Реальные backup и keepalive остаются на принятом приватном контуре до отдельного эксплуатационного GO и независимой проверки полного восстановления. Расписания GitHub из `main` не равнозначны принятию Writer/Scheduler.

Изменение общей схемы Supabase требует явной проверки совместимости с Writer/Verifier/Validation/PWA ([Issue #62](https://github.com/Alexio00/HEALTH/issues/62)). HIGH-риск подмены PWA scope-check [#50](https://github.com/Alexio00/HEALTH/issues/50) остаётся открытым; применима принятая владельцем ручная техническая приёмка по точному SHA, а не доверие только к CI.

## Воспроизводимость и переносимость

- `supabase/migrations/` — принятая timestamped история миграций; `db/migrations/` — сохранённые агрегированные исторические снимки, не альтернативный deployment-путь.
- Проверки Auth и политики доступа исполняемы через `scripts/validation/`. Полная историческая миграция выполнялась ограниченным `scripts/migration/full_migration.py` и **не должна повторяться** как способ технического обновления.
- PWA может размещаться на другом статическом хостинге без переноса медицинских идентификаторов. Source ID переживает смену физического провайдера; новую ссылку подтверждают по байтам и provenance.
- При disaster recovery Auth владельца можно воссоздать и перепривязать через `app_readers`; медицинские идентификаторы от Auth UUID не зависят.
