# HEALTH: маршрутизация веток и безопасный выпуск

Этот файл — инструкция для разработчиков и автоматизированных исполнителей при
работе с репозиторием. Медицинские правила и права записи задаются актуальными
приватными HealthDB Project Manual/Project State; этот файл их не заменяет.

## Перед любой задачей

1. Определи тип изменений: `frontend-only`, `Writer/backend`,
   `mixed`, `docs-only`. Проверь **живые** `main`, `pwa`, открытые PR,
   текущую ветку/базу и CI. Не предполагай, что номера коммитов из старого чата
   остаются актуальными.
2. Не коммить медицинские данные, REC, идентификаторы приватных источников,
   пароли, токены, личные сведения или рабочие конфигурации в GitHub.
3. Не меняй и не переписывай чужие параллельные ветки, не делай force-push
   и не закрывай/удаляй существующие PR без отдельного решения владельца.

## Разделение потоков

- **Веб-интерфейс** (страницы, навигация, CSS, статические ресурсы,
  service worker, браузерные тесты): начни ветку **от актуальной `pwa`**,
  направь PR **в `pwa`**. `pwa` — действующий источник GitHub Pages.
  Не отправляй такие PR в `main` ради публикации.
- **Writer, схемы Supabase, миграции, авторизация/OIDC, серверные проверки,
  исполнитель, резервное копирование**: отдельные ветки **от `main`**,
  PR **в `main`**; на `pwa` не переносить. Даже docs-only merge в
  `main` меняет SHA и требует согласованной процедуры принятия версии Writer.
- **Смешанные изменения** (например, Writer + фронтенд или документация +
  `frontend/README.md`): раздели на независимые PR и согласуй порядок.
  Пока это не сделано, не сливай смешанный PR ни в `main`, ни в `pwa`.
- **Документация**: инструкции по интерфейсу и выпуску меняй в `pwa`.
  Общая/Writer-документация должна пройти тот же контроль `main` SHA;
  подготовленный PR можно держать Draft до следующего согласованного принятия.
  Изменение Project State/Manual на приватном Drive — отдельная управляемая
  операция, не замена GitHub-PR.

## Если PR уже основан на неверной ветке

Простое переключение `base` недостаточно. Сначала сравни изменения с обеими
линиями и перенеси только необходимые коммиты/патчи (merge, rebase или
cherry-pick с проверкой). Разреши конфликты в `frontend/app.js`,
`frontend/styles.css`, `frontend/tests/contract.mjs`, `frontend/README.md`
по смыслу. Не возвращай удалённый «Мониторинг», не теряй полную ширину
раскрываемых карточек, REC-ссылки и группировку визитов. Сохрани имеющиеся
`frontend/oauth-test/*`; они уже находятся в `pwa`, даже если исходный
PR ещё открыт. При новых модулях проверь service worker и версию кэша.

## Защита выпуска PWA

Запрещено вносить прямые изменения в `pwa`: использовать только PR из
отдельной ветки, прошедший проверку `static` в `HEALTH code validation`.
В GitHub включены правила защиты ветки `pwa` (PR обязателен,
`static` обязателен, актуальная база, запрет force-push/удаления).
Это настройка GitHub, сам файл `AGENTS.md` **не создаёт защиту**.
Пока GitHub API сообщает `protected: false`, не заявлять, что прямые
push технически заблокированы. Подробности: `docs/PWA_RELEASE.md`.

Публикация из `pwa` теперь разделена на проверки/загрузку артефакта
и отдельный шаг Pages, ожидающий проверку (`needs: verify`).
Группа параллельности `pages-pwa` не пересекается со старой `pages`
в `main`. GitHub Pages environment должен разрешать только `pwa`.
Не перезапускать уже завершённый upload-job при наличии артефакта:
дубликат `github-pages` ломает deploy.

## Условия завершения

Для `pwa`: проверить diff относительно живой базы, синтетические тесты и CI;
после merge проверить автоматический GitHub Pages deploy **из `pwa`**
и браузерную работу под авторизованной сессией. Не путать CI PASS с
завершённым деплоем или ручной проверкой. Для повторного запуска Pages
создавай **новый** workflow run: re-run задания с уже загруженным
`github-pages` artifact может дать конфликт одинаковых артефактов.
При ошибках deployment использовать точный текст job logs.

Для `main`: до merge требуется план принятия **нового точного SHA**
в GitHub Actions variable, подписанном Edge broker и Supabase Writer
runtime с сохранением всех запретов. GitHub merge или зелёный CI
**не** являются таким принятием. Не обходить Writer прямым SQL/админскими
правами. После принятия сверить состояние и проверять авторизацию без
изменения медицинских данных. Параллельные изменения требуют координации.

**Текущая известная граница:** workflow, оставшийся в `main`, всё ещё
может развернуть GitHub Pages из `main`; это временный риск перезаписи
сайта. Если это случилось, повторно опубликуй утверждённый `pwa`.
Полное разделение идентичности Writer и публикации Pages — отдельный
проект со своим анализом безопасности и согласованным принятием.

Подробности и актуальная процедура: `docs/PWA_RELEASE.md` **в `pwa`**.

Изменения release controls требуют точного head SHA в owner PR; см. docs/PWA_RELEASE.md.
